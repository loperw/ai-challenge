# VPS: ветка 30

Цель: существующий чат-агент + Ollama на Ubuntu 24.04, 1 CPU / 2 ГБ RAM,
доступ через существующий VPN, без логина в чате.

## Состояние

Развернуто на VPS; доступ с телефона подтвержден пользователем.
Адрес сервиса и параметры частной сети хранятся только на сервере.
Node v24.21.0, Ollama 0.40.3, pnpm 10.34.7; модель qwen3:0.6b Q4_K_M.
Публичный доступ к чату и Ollama закрыт.

Службы: `chat-agent`, `chat-agent-network`, `ollama`.
Перед новой установкой создайте `/etc/chat-agent-network.env` по шаблону
`network.env.example`, заполните параметры своей сети и задайте права 600.
Конкретные адреса, интерфейсы и учетные данные не включаются в репозиторий.
`activate-private.sh` применяет эти параметры и генерирует локальный systemd drop-in.
## До установки

В VNC выполнить `bash inspect.sh` (или команды из этого файла).
Уточнить протокол VPN, расположение интерфейса/контейнера и маршруты телефона.
VPN на том же VPS не означает автоматически доступ к его внутренним сервисам.
Не менять существующие VPN-контейнеры, маршруты или firewall вслепую.
Потребуется SSH-пользователь и доступ ключом; секреты не помещать в репозиторий.

## Подготовка сервера после получения доступа

1. Проверить свободные RAM/диск и текущие службы. Сохранить конфигурацию firewall.
2. Установить Node.js 22.5+ (LTS с `node:sqlite`) и Ollama из официальных источников.
   Зафиксировать фактически установленные версии. Node из стандартного Ubuntu apt
   может быть слишком старым. Не переносить Windows node_modules и локальный .env.
3. Создать системного пользователя `chat-agent`, разместить исходники в
   `/opt/chat-agent`, установить зависимости по lockfile. Базу создавать новой;
   перенос истории с ноутбука выполнять отдельно, если он нужен.
4. Скачать `qwen3:0.6b` (523 МБ весов; рабочая RAM больше), записать digest.
   Это стартовый ресурсный компромисс, не улучшение качества относительно 2B.
5. Установить `ollama-override.conf` как
   `/etc/systemd/system/ollama.service.d/private.conf`; выполнить daemon-reload
   и restart Ollama. Проверить `OLLAMA_NO_CLOUD=1` и два parallel slots в логах.
6. Скопировать `chat-agent.env.example` в `/etc/chat-agent.env` и unit в systemd.
   Дать пользователю запись только в `/opt/chat-agent/data`.
7. Сначала запустить на loopback. После изучения VPN выбрать доступный
   VPN-адрес HOST и ограничить входящий трафик интерфейсом/подсетью VPN.
   При контейнерном VPN может потребоваться маршрут/прокси; универсального
   безопасного правила до инвентаризации нет. HTTP допустим только внутри
   зашифрованного туннеля. При отключенном VPN чат должен быть недоступен.
8. `systemctl enable --now chat-agent`, проверить health, логи и перезапуск.

## Ограничения профиля PRIVATE_LLM=1

- Только LOCAL_MODEL; облачные провайдеры отвергаются сервером.
- 2 параллельных потока к Ollama; третий получает 429, без неограниченной очереди.
- 12 изменяющих HTTP-запросов/минуту на IP, включая операции интерфейса.
  Если VPN скрывает устройства за одним IP, лимит общий для них.
- Контекст до 4096, ответ до 256 токенов, тело HTTP до 64 КиБ.
  В этом профиле maxTokens означает лимит ответа. Большие параметры отвергаются.
- Полный prompt проверяется консервативно по UTF-8 байтам с запасом на шаблон,
  поэтому длинный русский диалог может получить 413 раньше реального лимита токенов.
  Длинные системные инструкции, задачи, память и RAG могут не поместиться.
- Планировщик и внешние интеграции отключены; локальный провайдер не вызывает MCP.
  CSP блокирует внешние шрифты/браузерные подключения. При активации offline.conf
  сетевые ограничения systemd блокируют исходящие внешние соединения AI-служб.
- num_batch=64, q8_0 KV cache, Flash Attention и LLAMA_ARG_CACHE_RAM=0
  уменьшают RAM; runner использует два слота по 4096 токенов на одном CPU.
- Все устройства владельца видят общую историю; это однопользовательский сервис.
  Разные conversationId изолируют сообщения, один и тот же занятый чат возвращает 409.

## Проверки перед сдачей

С VPN-клиента с Node 22+: `CHAT_URL=http://VPN_IP:3000 node scripts/verify-vps.mjs`.
Скрипт сохраняемый через перенаправление stdout в JSON проверяет три пары потоков:
оба должны начать отдавать текст до окончания первого. Это проверка перекрытия
потоков, а не доказательство скорости или внутренних batch-операций модели.
Дополнительно проверить runner logs, память (`free -m`), OOM (`journalctl -k`),
поведение при третьем запросе и 13 запросах/минуту, большой контекст и неверную модель.
После перезапуска повторить health и генерацию. На телефоне проверить VPN on/off.
Если два запроса не проходят без OOM/таймаутов, конфигурация не принята;
понадобится больше RAM/CPU, а не скрытая последовательная очередь.

Резервная копия: остановить chat-agent и скопировать каталог data, затем запустить.
Ollama weights можно скачать повторно. Обновления сначала проверять отдельно;
не публиковать .env, ключи SSH/VPN и базы в Git.

## Управление установленным сервисом

```bash
systemctl status chat-agent ollama chat-agent-network
journalctl -u chat-agent -n 50 --no-pager
curl http://127.0.0.1:3000/api/health
systemctl restart chat-agent
```

После загрузки модели применен `/etc/systemd/system/ollama.service.d/offline.conf`.
Для намеренного обновления модели временно убрать этот drop-in, выполнить
daemon-reload и restart Ollama, скачать модель, затем вернуть drop-in и снова
перезапустить. Ключи облачных провайдеров на VPS не переносились.
