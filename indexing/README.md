# Локальная индексация PDF — ветка 21

В интерфейсе чата вкладка «Индексы» позволяет выбрать стратегию и включить
«Использовать книгу в ответах чата». Перед ответом сервер находит top-5 чанков
выбранного SQLite-индекса и передаёт их выбранной модели чата. Блок под ответом
показывает стратегию, найденные фрагменты, chunk_id, разделы и физические страницы PDF.
Ссылки «открыть страницу» открывают исходную книгу. Источники сохраняются вместе с
ответом и восстанавливаются после перезапуска. Для режима книги MCP-поиск по старой
базе отключён. Снятие флажка возвращает обычный чат с MCP.
Отдельная кнопка «Найти фрагменты» выполняет поиск только через локальную Ollama,
без вызова модели чата. Наличие фрагмента в top-5 не гарантирует его релевантность.

Пайплайн выполняется отдельно от чата, без отправки PDF облачным провайдерам:
PDF → текст с номерами страниц → чанки → Ollama → нормализованные векторы → SQLite.
Содержимое документа обрабатывается как данные. Индексация не обучает модель.

## Подготовка

Нужны Python 3.10+, зависимости `pip install -r indexing/requirements.txt`,
Ollama и модель `ollama pull nomic-embed-text`.
Ollama должна слушать `http://localhost:11434`; если не запущена, выполните `ollama serve`.
Для штатной установки: https://ollama.com/download/windows.
В этой рабочей папке также доступна локальная установка `data/tools/ollama/ollama.exe`
с CPU- и Vulkan-backend для GPU.
После перезапуска компьютера его можно запустить скрытым процессом:
`powershell -ExecutionPolicy Bypass -File scripts/start-index-ollama.ps1`.
Модели этого процесса сохраняются в `data/ollama-models/`, логи — в `data/tools/`.
Загрузка модели для локального варианта: `& ./data/tools/ollama/ollama.exe pull nomic-embed-text`.
Node-обёртка автоматически использует Python из bundled runtime Codex, если он доступен.
Для другой установки задайте `INDEX_PYTHON` — полный путь к Python.

```powershell
node scripts/document-index.cjs prepare "C:\Загрузки\Программирование на Kotlin для Android.pdf"
node scripts/document-index.cjs index "C:\Загрузки\Программирование на Kotlin для Android.pdf"
node scripts/document-index.cjs search data/document-index/structure.sqlite "Как работает null-безопасность в Kotlin?"
node scripts/document-index.cjs compare
```

Либо используйте `python indexing/pipeline.py` с теми же аргументами.
`prepare` не требует Ollama. Команда `index` создаёт обе базы; `compare` проверяет их на одинаковых запросах.
Параметры: `--size 1000 --overlap 150`, `--batch 16`, `--model nomic-embed-text`,
`--url http://localhost:11434`, `--output data/document-index`.
`search` и `compare` поддерживают `--top 5`.

## Две стратегии

* `fixed`: по 1000 символов, перекрытие 150 символов, возможны переходы между разделами.
* `structure`: границы по PDF-оглавлению и найденным заголовкам. Длинные разделы
  делятся по тем же 1000 символам с перекрытием 150; перекрытие не пересекает раздел.
  Небольшие разделы могут давать короткие чанки.

Размер указан в **символах Unicode**, не в токенах модели. Граница фиксированного
чанка может проходить внутри слова; перекрытие сохраняет соседний контекст.
Выбран небольшой размер: локальный GGUF этой модели содержит контекст 2048 токенов,
а русский текст расходует больше токенов на слово. `/api/embed` вызывается с `truncate=false`:
слишком длинный ввод вызывает ошибку, а не незаметную потерю текста.
Для Nomic добавляются префиксы `search_document:` и `search_query:`.
Модель и её digest сохраняются: поиск отклоняется при смене версии модели.

Если заголовок из оглавления не найден в тексте, граница берётся с начала его страницы
(`bookmark-page`). Совпадающие позиции объединяются. Без оглавления используется
консервативное распознавание нумерованных заголовков, иначе весь файл — один раздел.
Это приближение структуры; PDF не всегда содержит точную семантическую разметку.
Текст нормализуется, мягкие переносы склеиваются. Форматирование листингов не сохраняется.
Полностью сканированный PDF требует предварительного OCR; пустые страницы отражаются в отчёте.

## Результаты

В `data/document-index/` (исключён из Git):

* `fixed.sqlite`, `structure.sqlite`: таблицы `chunks` и `metadata`.
* `extracted.json`: текст, страницы и распознанные разделы.
* `fixed-chunks.json`, `structure-chunks.json`: читаемые чанки с метаданными.
* `preparation.json`: характеристики разбиения.
* `comparison.json`: фактическое время и размер индекса.
* `retrieval-comparison.json`: результаты поиска и метрики на контрольных запросах.
* `comparison.md`: читаемый отчёт о скорости, размере и результатах поиска.

Каждый чанк хранит `source`, `file`, `title`, `section`, `sections`, `chunk_id`,
`page_start`, `page_end`, стратегию, символьные позиции, число слов и текст.
`chunk_id` зависит от SHA-256 PDF, стратегии, параметров и границ фрагмента.
Номера страниц — **физические страницы PDF (от 1)**, не печатные номера книги.
Векторы сохраняются BLOB float32 little-endian; размерность записана в метаданных.
Поиск точный, по косинусному сходству, через NumPy; подходит для небольших локальных баз.
FAISS для этого объёма не требуется. SQLite можно открыть после перезапуска.
Перестроение каждой базы выполняется через временный файл и атомарную замену:
ошибка генерации не уничтожает предыдущую базу.

## Сравнение

Время индексации включает извлечение текста, разбиение, эмбеддинги и запись базы.
Первичная загрузка пакета/модели не учитывается. Прогрев модели измеряется отдельно.
Общее извлечение текста выполняется один раз, но включается в время обеих стратегий.
Стратегии выполняются последовательно, поэтому тайминги зависят от нагрузки и оборудования.
Размер индекса — размер готового `.sqlite`, без PDF, Ollama, модели и JSON-экспортов.

Для проверки поиска в `kotlin-queries.json` вручную заданы шесть запросов и страницы
с соответствующими фрагментами. `Hit@5` — доля запросов, для которых среди пяти
результатов есть нужная страница. `MRR@5` учитывает место первого такого результата.
Это небольшая проверка с разметкой по страницам, а не универсальная оценка качества.
Высокий cosine score сам по себе не означает правильный ответ.
Nomic v1.5 ориентирована на английский; качество на русском оценивается фактическим поиском.
