# AI Chat — интерфейс для нескольких AI-провайдеров

## Режимы ответа — ветка 22

Во вкладке «Индексы» выберите «С RAG» или «Без RAG».
С RAG сервер ищет пять релевантных чанков выбранной стратегии и передаёт их
вместе с вопросом модели. Под ответом сохраняются режим, тексты фрагментов,
разделы, chunk_id и ссылки на физические страницы PDF.
Без RAG поиск по книге не выполняется; остаются обычные MCP-инструменты чата.
Режим каждого нового ответа сохраняется в истории и виден после перезагрузки.
Для независимого ответа без контекста предыдущего режима создайте новый чат.
Выбор режима относится к обычному чату; режим задач и временные запросы
не используют поиск по книге. Ошибка поиска показывается пользователю,
а не подменяется ответом без RAG.

Поиск возвращает до пяти ближайших фрагментов без фильтрации по сходству.
Найденные фрагменты не гарантируют наличие ответа; модель сообщает, если нужной информации в них нет.

## Индексация PDF — ветка 21

Локальный пайплайн с двумя стратегиями chunking, эмбеддингами Ollama
`nomic-embed-text`, SQLite и сравнением поиска: [инструкция](indexing/README.md).
Запуск: `node scripts/document-index.cjs index "путь-к-документу.pdf"`.

Небольшое локальное веб-приложение для общения с моделями DeepSeek, OpenRouter и Gemini через API. Оно состоит из чата, изолированного серверного агента и правой панели настроек, где можно выбрать используемую модель и JSON-формат ответа.

## Возможности

- Отправка сообщений в DeepSeek V4.1 Flash, OpenRouter и Gemini API.
- Потоковая выдача для обычных запросов без MCP; при выборе инструментов сначала отображается живая трассировка, затем итоговый ответ.
- Модели разделены в списке на группы DeepSeek, OpenRouter и Gemini 3.5.
- Класс `Agent` хранит контекст диалога, применяет системный промпт и параметры генерации, вызывает API и разбирает потоковый ответ.
- Каждый чат получает отдельный экземпляр агента с изолированным стеком сообщений и сохранением в JSON.
- Восстановление диалогов после перезапуска, счётчик сообщений и очистка всей памяти.
- API-ключ не отображается в браузере и не передаётся клиентскому коду.

## Несколько MCP-серверов — ветка 20

Изменения реализованы в `codex/ai-challenge-20`. В Agent chat по умолчанию подключены четыре отдельных stdio-процесса. Реестр `mcp/servers.json` задаёт их ID, роль и `enabled`. Другой реестр можно указать через `MCP_SERVERS_FILE`. Поддерживаются встроенные роли из таблицы; для нового типа сервиса нужен новый адаптер. Изменения реестра применяются со следующего запроса.

| Сервер | Инструменты в каталоге модели | Данные |
| --- | --- | --- |
| `maps` | `maps__geocode`, `maps__route` | Города Open-Meteo/GeoNames, автомобильные маршруты OSRM/OpenStreetMap. |
| `weather` | `weather__get_weather` | Текущая погода и прогноз Open-Meteo. |
| `documents` | `documents__search`, `documents__combine_sources`, `documents__summarize`, `documents__saveToFile` | Локальная база знаний, объединение, выжимка и файл. |
| `schedules` | `schedules__schedule_task`, `schedules__list_schedules`, `schedules__get_schedule_results`, `schedules__set_schedule_status`, `schedules__delete_schedule` | Сохранённые расписания и результаты. |

Модель выбирает точное имя из общего каталога `tools/list`; реестр направляет вызов только в соответствующее соединение и передаёт серверу исходное имя инструмента. Одинаковые локальные имена на разных серверах не конфликтуют. Недоступный сервер отмечается в трассировке и исключается из каталога, остальные продолжают работать. Соединения закрываются после ответа или ошибки.

Пример длинного запроса:

> Построй автомобильный маршрут из Москвы (Россия) в Тулу (Россия), получи погоду в Туле на 3 дня, объедини маршрут и прогноз, кратко подведи итог и сохрани итог в trip.md. Также покажи мои текущие расписания.

Зависимости: два `maps__geocode` → `maps__route`; маршрут + `weather__get_weather` → `documents__combine_sources` → `documents__summarize` → `documents__saveToFile`. Независимый `schedules__list_schedules` и погода могут выполняться раньше или позже. Это восемь вызовов, выбранных моделью, а не фиксированный сценарий. Обычный запрос маршрута использует только карты; вопрос «2 + 2» не требует инструментов. Недостающие точки маршрута агент уточняет.

`placeId` для маршрута и `sourceId` для документов действуют только внутри одного хода. Клиент хранит успешные результаты и передаёт их точное содержимое между серверами приватным `_import_source`, скрытым от LLM. Импорт виден отдельно в трассировке; учитываются происхождение данных и порядок зависимостей. Будущие и чужие ID отклоняются. Выжимка объединённых данных берёт факты из каждого источника (при достаточном `maxSentences`), погодную часть агрегирует за весь период.

Карты и погода не требуют API-ключа; для выбора инструментов нужна настроенная языковая модель. Карты поддерживают **автомобильные маршруты между городами**, без пробок, улиц/домов, пеших маршрутов и общественного транспорта. При неоднозначном городе требуется уточнение региона. Публичный OSRM — демонстрационный сервис без гарантии доступности; HTTP-ошибки, таймауты и отсутствие маршрута возвращаются модели как ошибки. В одном процессе приложения вызовы карт сериализованы с паузой не менее 1,1 секунды. Данные и ссылки атрибутируются OSRM / © OpenStreetMap contributors. Контракты: [OSRM Route API](https://project-osrm.org/docs/v5.22.0/api/#route-service), [Open-Meteo Geocoding](https://open-meteo.com/en/docs/geocoding-api).

Проверки:

- `npm run mcp:list` — живое подключение всех серверов и объединённый каталог.
- `node --test` — настоящий stdio и подменённые внешние HTTP/LLM-ответы: восемь вызовов четырёх серверов, маршрутизация, зависимости, точность файла, изоляция ID, отказы, закрытие соединений и существующие сценарии.
- `npm run eval:multi-mcp` — реальная модель из `.env` и публичные API: маршрут, полный флоу, ответ без инструментов. Расходует токены LLM; проверяет состав вызовов, порядок зависимостей и содержимое файла. Отчёт с аргументами, результатами и трассировкой сохраняется в `data/evals/multi-mcp-*/report.json`. Независимые вызовы не обязаны иметь фиксированный порядок. Можно задать `EVAL_PROVIDER` и `EVAL_MODEL`.

Ниже локальные имена инструментов приведены без префиксов для краткости. Старый `mcp/server.mjs` без аргумента сохраняет совместимость с прямым клиентом и прежними тестами; Agent chat использует новый реестр.

## Автоматический MCP-пайплайн

В обычном Agent chat модель получает все доступные инструменты через параметр API `tools`: название, описание назначения и JSON Schema аргументов из MCP `tools/list`. Для DeepSeek и OpenRouter используется `tool_choice: "auto"`; для Gemini — нативные `functionDeclarations` и режим `AUTO`. Приложение исполняет только возвращённые моделью вызовы. Результат каждого `tools/call` поступает в следующий запрос к модели вместе с соответствующим `tool_call_id` (для Gemini — `functionResponse` и исходные thought signatures).

В коде нет обязательной последовательности инструментов и маршрутизации сообщений по ключевым словам. Модель может ответить без инструментов, выбрать один или построить цепочку. Описания и общий системный промпт объясняют зависимости: сначала получить необходимые данные, затем использовать фактический результат; поиск, сокращение и сохранение нужны только когда этого требует запрос. Отправка названий только текстом системного промпта не заменяет параметр `tools`.

| Инструмент | Назначение |
| --- | --- |
| `search` | Поиск в локальной базе знаний `mcp/knowledge.json`, **не веб-поиск**. Принимает `query`, необязательный `limit`; возвращает `results`, `text`, `sourceId`. |
| `summarize` | Выжимка из текста или погодных данных. Из текста выбирает значимые предложения; для прогноза считает диапазоны температур, вероятность осадков и частоту погодных условий за весь период. Принимает `sourceId` либо готовый `text`, необязательный `maxSentences`; возвращает `text`, новый `sourceId` и `inputSourceId`. |
| `saveToFile` | Сохраняет данные по `sourceId` либо `text` в UTF-8. Принимает простое имя `filename` с расширением `.txt`/`.md`. Возвращает карточку файла, размер в байтах и SHA-256. |

Созданные файлы отображаются карточками под ответом модели: имя, размер, **Предпросмотр** и **Скачать**. Предпросмотр открывает диалог с содержимым файла; закрыть его можно крестиком, клавишей Escape или нажатием вне окна. Текст показывается безопасно, без исполнения HTML. Скачивание возвращает исходный UTF-8 файл. Карточки сохраняются вместе с сообщением и восстанавливаются после перезагрузки. Локальный путь в ответе модели не выводится. Существующие ответы вида «Сохранено: путь» для доступных экспортированных файлов также показываются карточками.

Примеры для чата:

- «Найди в базе знаний сведения о MCP, сделай краткую выжимку и сохрани в summary.md» — ожидается поиск → выжимка → файл.
- «Найди сведения о MCP и покажи результаты, без сокращения и сохранения» — только поиск.
- «Сократи до одного предложения: MCP связывает приложение с инструментами. Сервер публикует каталог. Клиент вызывает инструменты» — только выжимка.
- «Сохрани точный текст “Привет, мир!” в hello.txt» — только запись.
- «Найди сведения о MCP и сохрани в raw.md без сокращения» — поиск → файл.
- «Сколько будет 2 + 2?» — ответ без инструментов.
- «Составь прогноз на неделю в Минске, кратко подведи итог и сохрани в файле» — `get_weather → summarize → saveToFile`. Прогноз возвращает `sourceId`, который передаётся в `summarize`; в файл записывается именно итог инструмента.

Явная просьба подвести итог трактуется системным промптом как операция `summarize`; модель не должна заменять её собственной выжимкой перед записью файла. Обычный прогноз без просьбы об итоге не требует `summarize`. Это правило выбора для LLM, а не маршрутизатор в коде: `tool_choice` остаётся `auto`, все инструменты доступны на каждом ходе.

По одному stdio-соединению на сервер живёт до конца запроса. `sourceId` ссылается на данные текущего хода: следующий инструмент читает ровно исходный результат, модель не должна переписывать его. Неверные и будущие ID, пустые источники, неправильные аргументы и ошибки файлов возвращаются модели с `isError`. Каталог не меняется в зависимости от ожидаемого шага. Все реально выбранные вызовы с аргументами и результатами видны во вкладке «MCP трассировка». Инварианты проверяются перед запросом и перед каждым действием инструмента.

По умолчанию файлы сохраняются в `data/exports`; путь задаётся через `PIPELINE_OUTPUT_DIR`. Каталог создаётся автоматически, существующие файлы не перезаписываются, пути вне каталога и системные имена запрещены. `PIPELINE_SEARCH_FILE` задаёт другой JSON-файл базы знаний — массив объектов `{ "title": "...", "text": "...", "source": "..." }`. Для обоих параметров рекомендуется абсолютный путь. Артефактные ID действуют только внутри текущего хода; файлы сохраняются между перезапусками.

За один запрос разрешено до 12 вызовов: это защита от бесконечного цикла, а не сценарий исполнения. Выполненные записи и расписания не откатываются при последующей ошибке LLM. Смотрите трассировку перед повтором запроса. В режиме задач инструменты доступны только на этапе исполнения утверждённого плана; в режиме сравнения моделей они отключены.

`node --test` проверяет реальные stdio-инструменты, передачу текста до файла, ошибки, отдельные вызовы, завершение без инструментов, ограничение цикла и API-контракты трёх провайдеров. Ответы LLM в этих тестах подменены: они проверяют исполнитель и передачу данных, но не качество выбора моделью.

`node scripts/eval-pipeline.mjs` (или `npm run eval:pipeline`) отдельно проверяет **реальную модель** на девяти сценариях, включая погоду с итогом, без итога и с сохранением исходных данных, и сохраняет запросы, ответы, аргументы, результаты и проверки точного содержимого файлов в `data/evals/pipeline-*/report.json`. Используется ключ из `.env`; проверка расходует API-токены. По умолчанию выбраны DeepSeek и `deepseek-flash`; `EVAL_PROVIDER` и `EVAL_MODEL` позволяют выбрать настроенный Gemini/OpenRouter. Модель OpenRouter должна поддерживать function calling. Автотесты не обращаются к платному API. Успешная проверка конкретной модели не гарантирует безошибочный выбор на любых формулировках.

Контракт function calling: [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/function-calling).

## Расписания и мониторинг

Запустите `node server.js` и напишите в обычном чате:

- `мониторинг погоды в Москве каждую минуту`
- `мониторинг погоды в Москве каждые 30 секунд`
- `погода в Минске каждые 5 минут`
- `напомни через 10 минут сделать перерыв`
- `напомни пить воду каждый час`

Модель выбирает MCP `schedule_task`, после успешного создания открывается вкладка **Мониторинг**. Погодный сбор начинается сразу, затем повторяется по расписанию (минимальный интервал — 30 секунд). Напоминание впервые срабатывает через заданный интервал. Поддерживаются интервалы в секундах, минутах, часах и днях и одноразовая задержка через `delaySeconds`. Создание через чат требует ключа языковой модели; последующий фоновый сбор и сводка работают без LLM и не расходуют её токены.

На вкладке находятся расписания из всех чатов, время следующего запуска, последний результат, история последних 30 запусков, счётчики успехов/ошибок и минимум, максимум и средняя температура. Интерфейс получает обновления раз в 3 секунды, сбор выполняется с заданным периодом. Температура у источника может обновляться реже: каждый сбор сохраняется с собственным временем получения и временем данных Open-Meteo. Пауза, продолжение и отмена доступны на карточке. Отмена окончательная; историю можно продолжать читать. Кнопка «Удалить» доступна у каждого мониторинга, включая завершённые и отменённые: она удаляет выбранное расписание вместе с его историей. Кнопка «Очистить всё» удаляет также все расписания и историю мониторинга. Выполняющийся сбор не восстановит удалённые записи. Очистка отдельного чата не отменяет расписания.

MCP-инструменты:

| Инструмент | Аргументы и результат |
| --- | --- |
| `schedule_task` | `kind: weather/reminder`, `location` или `message`, `intervalSeconds` и/или `delaySeconds`, необязательный `title`; возвращает сохранённое задание с ID. |
| `list_schedules` | Возвращает задания и статусы. |
| `get_schedule_results` | `id`, необязательный `limit` (1–100); возвращает `job`, агрегат `summary` и `runs`. |
| `delete_schedule` | `id`; удаляет выбранное расписание вместе с историей. |
| `set_schedule_status` | `id`, `status: active/paused/cancelled`; возвращает обновлённое задание. |

Расписания и результаты сохраняются в `data/schedules.sqlite` (WAL), отдельно от памяти чатов. Путь можно изменить через `SCHEDULE_DB_PATH` (предпочтительно абсолютный); он передаётся дочернему MCP-процессу. Хранятся последние 1000 запусков каждого задания. Температурная сводка рассчитывается по успешным сохранённым запускам; общие счётчики включают всю историю. MCP-соединение может завершиться сразу после создания задания: исполнитель живёт в процессе `server.js`.

Для работы **24/7** процесс `node server.js` должен постоянно работать на включённом компьютере или сервере без сна. Закрытие браузера не останавливает задания. Приложение само не включает компьютер и не устанавливает системную службу; для непрерывной эксплуатации настройте автозапуск и перезапуск процесса средствами хостинга или ОС. Уведомления сохраняются на вкладке мониторинга; системные push-уведомления и отправка сообщений во внешние сервисы не подключены.

После перезапуска просроченное задание выполняется один раз, пропущенные интервалы не воспроизводятся пачкой; следующие запуски сохраняют исходный ритм. Незавершённый запуск освобождается по истечении 60-секундной аренды. Атомарная аренда защищает от параллельного захвата, а результат и следующее время записываются одной транзакцией. При аварии сетевой запрос может повториться, но устаревший исполнитель не запишет результат. Ошибки источника видны в истории; периодическое задание повторяет попытку в следующий интервал, одноразовое завершается с сохранённой ошибкой. При паузе или отмене незавершённый результат отбрасывается.

Проверка: `node --test`. Тесты используют отдельные временные SQLite-базы и проверяют расписание, рестарт соединения, аренды, отмену, ошибки API, агрегаты, ограничение истории, исполнение выбранных LLM вызовов и реальные stdio-вызовы MCP.

## MCP-инструмент погоды

Локальный MCP-сервер в `mcp/server.mjs` регистрирует `get_weather`. Инструмент принимает `location`, `days` и `units`, вызывает геокодер и прогноз Open-Meteo, а затем возвращает текстовый и типизированный `structuredContent`. Для самого Open-Meteo API-ключ не нужен; выбор инструмента в чате выполняет настроенная LLM.

Для запроса вроде «Какая погода в Москве на 3 дня?» модель может вызвать `get_weather` прямо из Agent chat. Продолжение «а в Минске» интерпретируется моделью по истории диалога. Правый таб «MCP трассировка» показывает выбранные инструменты, JSON Schema, фактические аргументы и ответы; при новом сообщении прежняя трассировка очищается.

После установки зависимостей запустите:

```bash
npm run mcp:list
```

В консоли будут выведены версия MCP-сервера и схемы всех зарегистрированных инструментов. Отдельно запускать `mcp/server.mjs` не нужно: это делает `StdioClientTransport`.

## Задачи

Под стрелкой отправки находится компактная кнопка «Задача». Она создаёт задачу прямо из введённого сообщения, закрепляет выбранный профиль и формирует название вида «Задача: …» без дополнительного диалога. Исходный текст сразу становится первым сообщением пользователя в диалоге задачи. Внутренние команды автомата в переписке не показываются. Задача — отдельная сущность: она не смешивается с историей чатов, хранит собственный профиль, сообщения и память и проходит формализованные этапы `planning → awaiting_approval → execution → validation → done`. Пауза — отдельное состояние, из которого можно вернуться только в сохранённый `resumeStage`.

Верхняя шкала показывает этап и текущее действие. На вкладке «Процесс» находятся название, текущий шаг, ожидаемое действие и статусы шагов плана. При планировании агент сначала объясняет, что будет происходить при выполнении и как будет получен результат, а затем формирует только необходимые шаги — обычно один-два, без искусственного дробления. Основная кнопка меняется вместе с состоянием: «Сформировать план», «Утвердить план», «Выполнить шаг …» и «Проверить результат»; нажатия появляются в диалоге как короткие сообщения пользователя с теми же названиями. Внутренние инструкции при этом остаются скрытыми. Паузу можно включить на любом незавершённом этапе; продолжение восстанавливает тот же этап, шаг и план. «Пересмотреть план» открывает отдельный диалог с причиной изменений. После перехода в `done` поле сообщений остаётся доступным.

## Память агента

- Краткосрочная память — сообщения текущего чата. Пользовательские сообщения и ответы агента показаны отдельными пунктами.
- Рабочая память — цели и ограничения текущей задачи. Команда `/working текст` добавляет запись только в активный чат.
- Долговременная память — профиль, решения и знания для всех чатов. Команда `/long текст` делает запись доступной каждому диалогу.

Персонализация вынесена в отдельные профили. В левой панели можно создать пользователя, указать род деятельности, язык, предпочтительный формат ответа и ограничения, выбрать активный профиль или отредактировать и удалить его через кнопку с шестерёнкой. Выбранный профиль добавляется сервером в системный контекст каждого запроса к модели; в истории диалога хранится только идентификатор профиля, а сами профили находятся в отдельной таблице SQLite.

Команды памяти сохраняются без запроса к LLM и помечаются в переписке отдельным оформлением. Краткосрочные сообщения, рабочие записи и долговременная память хранятся в отдельных таблицах SQLite-базы `data/agent-memory.sqlite`; агент добавляет рабочие и долговременные записи в системный контекст перед обычным запросом. Очистка текущего чата удаляет его краткосрочную и рабочую память, но сохраняет долговременную. «Очистить всё» удаляет все три типа.

## Подсчёт токенов

Правая панель показывает оценку текущего запроса (при вводе — черновика), всей истории без приветствий и ошибок, а также вход, ответ и суммарный расход последнего вызова API. История — объём сохранённого текста, а не сумма расходов всех вызовов: прежние сообщения отправляются повторно.

`public/token-counter.js` использует грубую эвристику: 1/4 токена на ASCII-символ и 1/2 на прочие Unicode-символы с округлением вверх. Это не токенизатор модели; оценки помечены ≈ и не включают служебную разметку сообщений. `Agent` читает фактические `usage` / `usageMetadata` из потока, включая финальные события без текста. При отсутствии данных API остаётся оценка. Суммарный расход и выход API могут включать внутренние рассуждения, в зависимости от провайдера.

Поле «Лимит токенов диалога» задаёт общий бюджет истории запросов и ответов, включая системную инструкцию. Перед каждым вызовом агент вычитает оценку всей истории и нового запроса из бюджета, а остаток передаёт как `max_tokens` (DeepSeek/OpenRouter) или `maxOutputTokens` (Gemini). При исчерпании бюджета запрос отклоняется без изменения сохранённой истории. Пустое поле отключает общий лимит. Расчёт приблизительный: используется оценка текста, а не токенизатор конкретной модели.

Форматы статистики: [DeepSeek](https://api-docs.deepseek.com/api/create-chat-completion/), [OpenRouter](https://openrouter.ai/docs/cookbook/administration/usage-accounting), [Gemini](https://ai.google.dev/api/generate-content).

## Запуск локально

Для встроенного модуля SQLite требуется Node.js 22.5 или новее.

1. Создайте файл `.env` рядом с `server.js`, скопировав содержимое `.env.example`.
2. Укажите ключи тех сервисов, которыми планируете пользоваться:

   ```env
   DEEPSEEK_API_KEY=ваш_ключ_DeepSeek
   OPENROUTER_API_KEY=ваш_ключ_OpenRouter
   GEMINI_API_KEY=ваш_ключ_Gemini
   AGENT_SYSTEM_PROMPT=необязательный системный промпт агента
   ```

3. Запустите сервер:

   ```bash
   node server.js
   ```

4. Откройте [http://localhost:3000](http://localhost:3000).

Открывать `public/index.html` напрямую как локальный файл не нужно: запросы чата обслуживает Node.js-сервер. Если интерфейс сообщает, что сервер недоступен, снова выполните `node server.js` и обновите страницу по адресу выше.

## Безопасность ключа

Файл `.env` включён в `.gitignore`, поэтому не будет добавлен в Git и опубликован на GitHub. В репозитории остаётся только `.env.example` без настоящего ключа.

При публикации приложения на сервере добавьте нужные переменные окружения (`DEEPSEEK_API_KEY`, `OPENROUTER_API_KEY`, `GEMINI_API_KEY`) в настройках хостинга, а не в исходный код.

`AGENT_SYSTEM_PROMPT` задаёт необязательную общую системную инструкцию. В интерфейсе доступны модель и JSON-режим. История завершённых запросов и ответов сохраняется транзакционно в SQLite-базе `data/agent-memory.sqlite` (исключена из Git) и загружается после перезапуска. При первом запуске существующие `data/conversations.json` и `data/memory.json` автоматически импортируются и остаются резервными копиями. Незавершённый из-за остановки сервера ответ не сохраняется. «Очистить» удаляет текущий диалог, «Очистить всё» удаляет все сохранённые диалоги и локальную копию браузера. Во время генерации очистка памяти отклоняется, чтобы ответ не восстановил удалённый контекст. Счётчик учитывает пользовательские запросы и ответы агента, без приветствий и ошибок.
# Управление контекстом

Переключатель в настройках каждого чата выбирает одну из трёх стратегий. По умолчанию Sliding Window; summary не создаётся и прежнее summary не отправляется модели.

- **Sliding Window**: запрос содержит последние N сообщений, включая текущее сообщение пользователя. После ответа сохраняются только последние N сообщений. Старые сообщения удаляются и не восстанавливаются при увеличении N.
- **Sticky Facts**: перед каждым ответом отдельный вызов выбранной модели обновляет JSON facts (ключи и строковые значения): цели, ограничения, предпочтения, решения, договорённости. Основной запрос содержит facts + последние N сообщений. Старые сообщения удаляются. Некорректные facts или ошибка ответа откатывают весь ход. Расход обновления памяти показан отдельно, вне бюджета основного ответа.
- **Branching**: попросите варианты (например, виды отпуска). После ответа со списком нажмите «Создать ветки из вариантов ответа»: каждый пункт станет отдельной веткой с названием этого вида отпуска. Выберите вариант в селекторе и продолжайте разговор — модель получает выбранную тему вместе с историей ветки. Общая история до списка сохраняется как checkpoint, дальнейшие сообщения каждой ветки независимы. Названия сохраняются при новых ответах. Повторное нажатие для того же ответа не создаёт дубликаты. Поддерживаются нумерованные и маркированные списки, а также Markdown-заголовки. N в этой стратегии не применяется.

Сообщение пользователя и ответ считаются отдельно. Checkpoints, ветки, активная ветка и facts сохраняются в SQLite и восстанавливаются после перезапуска. Checkpoint неизменяем: продолжение ветки его не меняет. Очистка чата удаляет и его ветки. Переход в другую стратегию использует доступные сообщения; ранее отброшенные сообщения не возвращаются. При создании веток checkpoint сохраняется автоматически.
