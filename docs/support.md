# Поддержка пользователей — ветка 33

Откройте `/support.html` или ссылку «Поддержка» в правой панели AI Chat.
Запуск: `npm start`. Требуется существующий `DEEPSEEK_API_KEY` в `.env`.
Генерация выполняется только через DeepSeek (`deepseek-flash`). Ollama не нужна.
В режиме `PRIVATE_LLM=1` сервис возвращает явную ошибку, без переключения на локальную модель.

## Демонстрационные данные

SupportDesk — вымышленный продукт. `support/demo.json` содержит три тестовых профиля
и четыре тикета: обязательный SSO, истёкшая ссылка восстановления, временная блокировка
и экспорт CSV. `support/knowledge.json` содержит FAQ и инструкции этого продукта.
Это не данные реальной CRM и не описание правил AI Chat.

`mcp/support-server.mjs` предоставляет настоящие MCP tools `list_users`, `list_tickets`
и `get_context`. Сервер приложения получает их через stdio MCP-клиент; JSON не
передаётся модели напрямую в обход MCP. `get_context` проверяет принадлежность тикета
выбранному пользователю. `SUPPORT_DATA_FILE` позволяет задать другой файл того же формата.
Внешняя CRM пока не подключена.

## RAG и контекст

Отдельный лексический индекс FAQ строится в памяти при запросе. BM25 ранжирует
фрагменты по вопросу с простым нормированием русских слов. Данные тикета повышают
ранг уже совпавших материалов, но не добавляют нерелевантные документы. Короткие
уточнения дополняются последними вопросами пользователя. До трёх найденных фрагментов,
профиль, тикет и история передаются DeepSeek. Это лексический RAG без эмбеддингов;
сложные перефразирования могут потребовать расширения тегов FAQ.

Ответ включает ссылки `[id]` на FAQ и `[MCP: T-...]` на тикет. Под ответом отображаются
найденные источники с текстами и фактический контекст MCP. Ссылки показывают найденные
документы; программной проверки истинности каждого утверждения модели нет.
При отсутствии сведений ассистент должен уточнить вопрос или направить к сотруднику.
Ошибка MCP возвращается пользователю и не подменяется ответом без контекста.

История хранится в sessionStorage браузера отдельно для каждой пары пользователь/тикет,
до 12 сообщений; при перезагрузке восстанавливается текст. Карточки источников остаются
только у ответов текущей загрузки страницы. Кнопка очистки удаляет историю текущей пары.

## API

- `GET /api/support/users` — список пользователей через MCP.
- `GET /api/support/tickets?userId=u-101` — обращения пользователя через MCP.
- `GET /api/support/source/sso` — текст источника FAQ.
- `POST /api/support/chat` — `{userId, ticketId?, message, history?}`; ответ JSON
  `{answer, sources, context, trace, provider, model}`. История содержит только роли
  `user` и `assistant`. Клиент не может выбирать локальную модель.

Это локальный демонстрационный интерфейс, не система авторизации: любой посетитель
может выбрать тестовый профиль. До подключения реальных данных нужны проверка сессии
и прав на сервере, серверное хранение истории и аутентификация интеграции CRM.

## Проверка

`node --test test/support.test.js` проверяет поиск, валидацию, реальное MCP-соединение,
отказ для чужого тикета и недоступные данные без вызова какой-либо модели.

`npm run eval:support` запускает изолированный сервер с временной БД и выполняет
реальные запросы к DeepSeek. Скрипт блокирует все иные upstream fetch-вызовы,
включая локальные модели и эмбеддинги. Результат: `data/support-evaluation.json`.
Проверяются разные причины авторизации, уточнение, экспорт, неизвестный SLA,
общий вопрос без тикета, чужой и несуществующий тикеты, запрет локального провайдера.
